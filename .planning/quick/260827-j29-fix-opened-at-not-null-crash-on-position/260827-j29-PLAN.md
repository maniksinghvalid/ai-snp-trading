# Quick Task 260827-j29: Fix opened_at NOT NULL crash + missing force_close job

## Origin

Live incident, 2026-08-27 13:45 ET. The equity bot took a Trend Join Long entry
in US.CRM (20 sh @ 251.98, order 861672). The fill was detected, then
`register_position` raised and the position was never managed:

```
sqlite3.IntegrityError: NOT NULL constraint failed: positions.opened_at
  bot/service/bot.py:314   register_position(pos)
  bot/position/manager.py:1372 _persist_position(...)
  bot/state/store.py:311   upsert_position(...)
```

Because `register_position` raised, neither `on_fill()` (FSM → ACTIVE) nor
`arm_stop_protection()` ran: 20 filled shares sat at the broker with no stop,
no partial, no trail and no force-close, invisible to reconcile (no DB row →
"not_bot_owned").

Same session, a second defect: `_reschedule_force_close` logged
`JobLookupError: 'No job by the id of force_close was found'` on both 2026-08-26
and 2026-08-27, so no force-close was armed on either day.

## Root causes

1. **`opened_at` never stamped on the AWAITING_FILL path.**
   `bot/service/bot.py:301` constructs `PositionState` without `opened_at` /
   `updated_at` (both default to `None`). `positions.opened_at` and
   `positions.updated_at` are `NOT NULL` (migration 0001). `opened_at` is only
   assigned later, in `manager._on_entry_fill` (manager.py:703) — which the
   crash prevents from ever running. The existing test
   (`TestRegisterPosition`) passes because its `_make_pos` factory always
   supplies both timestamps, so it never exercised the production shape.

2. **One-shot `DateTrigger` job is auto-removed after it fires.**
   `force_close` is registered as a `DateTrigger` (bot.py:473) parked at 2099
   and re-pointed daily by `_reschedule_force_close` via
   `scheduler.reschedule_job("force_close", ...)`. Once it fires, APScheduler
   removes the job ("Removed job force_close", 2026-08-25 19:51). The bot stayed
   up across days, so every later `reschedule_job` hit a job id that no longer
   existed. The `except Exception` swallows it, leaving the session unarmed.

## Tasks

### Task 1 — Stamp opened_at/updated_at in register_position

- **files:** `bot/position/manager.py`, `tests/position/test_manager.py`
- **action:** In `register_position`, default `pos.opened_at` / `pos.updated_at`
  to `now_et()` when `None`, before the DB-first `_persist_position` call. Fix
  goes in the shared method, not the caller, so every present and future caller
  is covered. `_on_entry_fill` still overwrites `opened_at` with the real
  `fill.fill_time` moments later, so the stamp is a crash-safe placeholder that
  matches the `adopt_orphan` convention (manager.py:1428).
- **verify:** New test builds `PositionState` exactly as `bot.py:301` does
  (no timestamps) and asserts `register_position` persists without raising.
  Test must fail against the unpatched method.
- **done:** `pytest tests/position/test_manager.py` green.

### Task 2 — Make force_close rescheduling survive a fired job

- **files:** `bot/service/bot.py`, `tests/service/test_bot.py`
- **action:** Replace `scheduler.reschedule_job("force_close", ...)` in
  `_reschedule_force_close` with `scheduler.add_job(..., id="force_close",
  replace_existing=True)`, which both re-points a live job and re-creates one
  that already fired.
- **verify:** New test removes the `force_close` job, calls
  `_reschedule_force_close(today)`, asserts the job exists again at today's
  calendar-aware close time.
- **done:** `pytest tests/service/test_bot.py` green.

### Task 3 — Full suite

- **action:** Run `python3 -m pytest -q`.
- **done:** No new failures vs. the pre-change baseline.

## Out of scope

- Whether `force_close_reschedule_error` should alert rather than only log.
