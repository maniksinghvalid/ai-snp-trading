# Quick Task 260827-j29 — Summary

Two defects from the same live session (2026-08-27), both of which left a filled
position unprotected. Found while answering "how was the CRM order placed".

## Task 1 — `opened_at` NOT NULL crash on register_position ✅

`bot/service/bot.py:301` builds an AWAITING_FILL `PositionState` with no
`opened_at` / `updated_at`; both columns are `NOT NULL` (migration 0001), so the
DB-first `upsert_position` raised `sqlite3.IntegrityError` and the exception
propagated out of `_process_bar`. `on_fill()` (FSM → ACTIVE) and
`arm_stop_protection()` never ran.

Fixed in `PositionManager.register_position` — the shared method, so every
caller is covered — by stamping `now_et()` for whichever timestamp is `None`
before persisting. `_on_entry_fill` still overwrites `opened_at` with the real
`fill.fill_time` immediately afterwards, so the stamp is only a crash-safe
placeholder. Same convention `adopt_orphan` already used (manager.py:1428).

Regression test builds the `PositionState` exactly as `bot.py` does and asserts
persistence. Confirmed RED before the fix with the production traceback
(`NOT NULL constraint failed: positions.opened_at`). The pre-existing
`TestRegisterPosition` never caught this because its `_make_pos` factory always
supplied both timestamps.

## Task 2 — force_close job vanished after firing ✅

`force_close` is a one-shot `DateTrigger`; APScheduler removes it once it fires
("Removed job force_close", 2026-08-25 19:51). The bot stayed up across days, so
each morning `_reschedule_force_close` called `reschedule_job` on a job id that
no longer existed → `JobLookupError`, swallowed by the surrounding `except`.
2026-08-26 and 2026-08-27 ran with no force-close armed.

`reschedule_job` now falls back to `add_job` when the job is gone, logging
`force_close_job_recreated`. `add_job(replace_existing=True)` was tried first and
rejected: a *pending* job (scheduler not yet started — the mid-session arm path
in `_register_jobs`) is not deduplicated by `replace_existing`, and two existing
tests correctly caught the resulting duplicate `force_close` job.

Regression test removes the job, reschedules, and asserts it is back at today's
calendar-aware close time. Confirmed RED with the production `JobLookupError`.
