<objective>
Build `BacktestHarness` (BT-01) — the replay controller that ports
`bot.service.bot.TradingBot._process_bar` bar-for-bar and wires the reused live pipeline
(`TrendJoinLong`, `SignalEngine`, `RiskEngine`, `PositionManager`) against the two simulated
leaves (`SimulatedBarFeed`/`SimulatedExecution` + `SimulatedGateway`). This is where
"confirming live/backtest code parity" is realized: the strategy/signal/risk/FSM code is
imported UNCHANGED; only `gateway`/`execution` differ.

Two load-bearing constraints, both verified against source:

1. CLOCK CONTROL (not in 06-RESEARCH): `SignalEngine` reads wall-clock
   `bot.signal.signal_engine.now_et()` for BOTH the entry-window gate (`_in_entry_window`) and
   the session-date key (`session_date_str = now_et().date()`) that drives
   `get_rvol_baseline`/`get_tod_baseline`/filled-count/circuit-breaker lookups. Replaying a
   historical bar against the real wall clock would evaluate the entry window and baseline keys
   against TODAY, not the bar's date — silently wrong. The harness MUST make `now_et` return the
   current replay bar's ET time. This is a runtime monkeypatch of the module attribute, NOT a
   `bot/` source edit, so BT-01's "no modifications to live code" holds.

2. TRADE-LOG CAPTURE (overrides 06-RESEARCH's get_closed_trades note): no `bot/` code writes the
   `trades` table, so the report can't read it. The harness captures each position as it reaches
   CLOSED (entry_price, exit_price from SimulatedExecution's exit_fills, quantity, exit_reason
   from pos.pending_exit_reason, r_multiple) into a trade-log list for 06-04's report.

Scope boundary (06-RESEARCH Open-Q2): this harness replays the CURRENT `partial_be_trail` exit
model FSM only. `fixed_2r`/`full_to_1p5r_trail` are schema-only stubs owned by Phase 7 (07-06)
— out of scope here.
Output: `backtester/harness.py`, filled `tests/backtester/test_harness.py`.
</objective>
