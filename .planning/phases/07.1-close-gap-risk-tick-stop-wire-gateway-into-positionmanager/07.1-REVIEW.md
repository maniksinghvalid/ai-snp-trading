## Summary

to the `PositionManager(...)` construction call) plus a new regression test file,
`tests/test_main_wiring.py`, that drives `bot.main.main()`'s real construction sequence to

and they do exercise the real `PositionManager` instance built by `main()`'s production

No Critical issues found. The fix is correct and the regression test genuinely closes the

## Warnings

### WR-01: Second test's pass/fail is silently coupled to `rules.json`'s current config value, not asserted

**File:** `tests/test_main_wiring.py:77-104`
**Issue:** `test_armed_stop_dispatches_through_real_construction` asserts
`mock_gateway.subscribe_quote.called`, which is only correct because the *current* shipped
`rules.json` has `use_broker_stop_orders: false` (verified: `rules.json:60`). The test's own
docstring acknowledges this ("If that flag is ever flipped to true, the asserted dispatch
becomes `gateway.place_stop_order`") but does not act on it — there is no assertion that pins
the precondition, and no branch that checks the actual config value before choosing which
mock attribute to assert on. If a future change to `rules.json` flips
`use_broker_stop_orders` to `true` for an unrelated reason (e.g. enabling broker-side stops
in production), this test starts failing with `subscribe_quote` never called — which looks
like a wiring regression (the exact class of bug this file exists to catch) but is actually
just a stale test assumption. That false-positive erodes the signal this regression suite is
meant to provide, and someone debugging the failure has no fast way to tell the two apart
from the assertion message alone.
**Fix:** Assert the precondition explicitly so the failure mode is obvious, and dispatch the
assertion accordingly:
```python
captured_pm, mock_gateway = _drive_real_main(monkeypatch)
use_broker = captured_pm._cfg.use_broker_stop_orders
...
_real_asyncio_run(captured_pm.arm_stop_protection(pos))

if use_broker:
    assert mock_gateway.place_stop_order.called, "..."
else:
    assert mock_gateway.subscribe_quote.called, "..."
```

**File:** `tests/test_main_wiring.py:19`
**Issue:** `pytest` is imported but never referenced (`grep -n "pytest\."` finds no usage —
no `pytest.mark`, `pytest.raises`, `pytest.fixture`, etc.). Both test functions are plain

```python
import asyncio
from unittest.mock import AsyncMock, MagicMock

import bot.main

```

### IN-02: Construction-step comment labels are out of chronological order

**File:** `bot/main.py:78-112`
**Issue:** The inline step comments read `5a` (strategy/engine), `5d` (signal engine), `5e`
(risk engine), `5b` (alerter), `5c` (position manager) — i.e. execution order is
a → d → e → b → c, not a → b → c → d → e. This is pre-existing (not part of this phase's
diff) but it is in a file under review and makes it harder to correlate the module
docstring's numbered "Construction order" list (lines 45-57, which lists 5, 5d, 5e in that
order and omits 5a/5b/5c entirely) with the actual code sequence below it. Not a functional
bug — construction order is otherwise correct and verified against downstream dependencies
(`RiskEngine` needs `signal_engine` already constructed, which it is).
**Fix:** Relabel the steps to match execution order (e.g. `5a` strategy/engine, `5b` signal
engine, `5c` risk engine, `5d` alerter, `5e` position manager) or drop the sub-lettering and
rely on the surrounding prose, whichever is less churn.
