<objective>
Close the two BLOCKERS and four lesser findings from `06.1-08-REVIEW.md`. Plan 06.1-08 opened
SQLite with `check_same_thread=False` + a `threading.RLock` exposed via `lock()` and wrapped
~7 access sites (3 store accessors + 4 executor jobs). That fixed the *crash* but left ~13 other
writers/readers of the shared `store.conn` UNGUARDED (reconcile_once on the event-loop thread, the
engines, the manager, the scanner, signal_engine). The reconcile loop `await`s mid-write while a
lock-holding worker job runs concurrently on the same connection, converting the loud
`sqlite3.ProgrammingError` into SILENT data corruption / `row_factory` races /
`recursive use of cursors`. The regression test added in 06.1-08 only drives worker-thread READS,
so it is green even with the race unfixed (false confidence).

This plan implements the operator's LOCKED architecture: Encapsulate in StateStore. Route ALL
database access through guarded `StateStore` methods, each acquiring `self._lock` around a SHORT,
PURELY-SYNCHRONOUS block (`conn.execute(...); conn.commit()` plus any `row_factory` flip/reset)
with NO `await` inside the locked region. Stop exposing the raw `conn` for mutation so no caller
can forget the lock or hold it across an await. This resolves CR-01, CR-02, and WR-02 together;
adds WR-03 (`busy_timeout`); and corrects the IN-01 comment.

Purpose: Make the single shared SQLite connection genuinely serialized across the asyncio
event-loop thread and the four ThreadPoolExecutor worker threads, so SAFE-03 reconciliation and
the POS-03 trailing-stop write path cannot silently corrupt position/intent state.
Output: A fully-encapsulated StateStore (every DB op a guarded method), all callers migrated off
raw `conn`, a busy_timeout, an accurate invariant comment, and a RED-first concurrency regression
test that actually drives the loop-vs-executor race.

## Why this design (locked — do not propose alternatives)

The 06.1-08-REVIEW lists two viable fixes; the operator chose approach #1 (encapsulate in
StateStore) over approach #2 (sprinkle `store.lock()` at every raw-conn call site). Encapsulation
is strictly safer because it makes the lock impossible to forget: a future maintainer cannot add a
new unguarded `conn.execute` if `conn` is no longer exposed for mutation. Approach #2 would also
require holding the lock across the reconcile-loop `await`s (CR-02 deadlock) unless every call site
were manually decomposed; pushing the lock DOWN into short sync store methods does that
decomposition once, structurally.
</objective>
