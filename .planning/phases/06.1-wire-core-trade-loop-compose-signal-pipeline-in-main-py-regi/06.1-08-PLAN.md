<objective>
Close the single UAT blocker for Phase 06.1: `sqlite3.ProgrammingError: SQLite objects created
in a thread can only be used in that same thread`. The StateStore connection is opened with the
default `check_same_thread=True`, binding it to the main thread. The four scheduled jobs in
`bot/service/bot.py` hand `self._store` into `loop.run_in_executor(None, ...)` worker threads
where `conn.execute`/reads run on a different thread, raising ProgrammingError. This was masked
in the suite because every test exercises these store paths synchronously (same thread).

Purpose: Make all four executor jobs thread-safe so the live trade loop runs unattended, and add
a cross-thread regression test so the crash is caught by the suite, not only live.
Output: A thread-safe StateStore (check_same_thread=False + serialized access), executor jobs that
serialize their store access through the store lock, and RED-first regression tests.

## Thread-safety strategy (chosen + justification)

**Chosen strategy: open the connection with `check_same_thread=False` AND serialize every use of
the connection object through a single re-entrant lock (`threading.RLock`) owned by the StateStore.**

Why this one, over the alternatives:

- **Why not connection-per-thread / short-lived connection-per-job:** The bot is a single-writer
  paper-trading process using WAL journal mode. Per-thread connections would each need their own
  WAL checkpoint coordination and would not see each other's uncommitted state; the existing 20+
  `store.conn.execute` call sites across manager.py, engine.py, risk_engine.py, signal_engine.py,
  scanner.py, and gateway.py all assume one shared connection. Swapping the connection model is a
  large blast radius for a single-blocker hotfix.
- **Why not marshal writes back to the event loop:** The executor jobs (`run_daily_scan`,
  `run_intraday_rescan`, the EOD fetch/build/write) are coarse, synchronous, multi-statement
  operations that the design deliberately pushes off the event loop to avoid blocking it. Marshaling
  them back onto the loop thread re-introduces the loop-blocking they were moved off to avoid.
- **Why `check_same_thread=False` alone is NOT enough — the concurrency risk is real:** The
  event-loop thread also WRITES to the same connection. `PositionManager` writes via
  `upsert_position` (store.py:249/278) and `self._store.conn.execute(...)` + `.commit()`
  (manager.py:965/973, 998/1003); `ExecutionEngine` writes at engine.py:462/467; the SAFE-03
  `reconcile_once`/gateway path writes at gateway.py:840+. These run on the loop thread on every
  closed 5m bar and during reconciliation. The store's read methods also MUTATE shared connection
  state (`self._conn.row_factory = sqlite3.Row` then reset to `None`, store.py:293/298, 313/318).
  With `check_same_thread=False` but no lock, an executor-thread scan write can interleave with a
  loop-thread manager write or a row_factory flip → corrupted reads / inconsistent cursor state.
  Therefore the connection MUST be serialized by a lock.

**Implementation shape:**
1. `StateStore.__init__` creates `self._lock = threading.RLock()` (re-entrant so a locked public
   method can call another locked public method without deadlock).
2. `StateStore.open()` opens with `sqlite3.connect(self._db_path, check_same_thread=False)`.
3. `StateStore` exposes `lock()` returning the RLock as a context manager (`with store.lock():`).
4. The store's own read/write methods that mutate connection state (`get_open_positions`,
   `get_closed_trades`, `upsert_position`, and any other row_factory-flipping reader) wrap their
   body in `with self._lock:` so the row_factory flip + fetch + reset is atomic.
5. The four executor jobs in `bot/service/bot.py` wrap the store-touching call in
   `with self._store.lock():` so a whole scan/subscribe/report store operation is serialized
   against the loop-thread manager/engine writes. RLock means a job that calls a store method that
   also locks does not deadlock.

This keeps the existing store API surface and the 20+ direct call sites intact (paper-trading
single-writer, no real-money path touched), eliminates the ProgrammingError, and closes the
cross-thread write race.
</objective>

| event-loop thread ↔ executor worker threads | The same sqlite3.Connection object is used across the asyncio event-loop thread (position-manager / execution-engine / reconcile writes) and ThreadPoolExecutor worker threads (the four scheduled jobs). Cross-thread access to one connection is the defect. |
| OpenD localhost | Unchanged this plan — no new external surface; paper (SIMULATE) only. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06.1-08-01 | Denial of Service | StateStore connection used across threads | mitigate | Open with check_same_thread=False so the connection is usable from executor workers; the ProgrammingError that aborts the scheduled jobs (and silently starves the bar pipeline of watchlist data) no longer fires. |
| T-06.1-08-02 | Tampering | Concurrent writes (executor scan/report vs loop-thread manager/engine) to one connection | mitigate | Serialize all connection use behind a store-owned threading.RLock; row_factory-flipping readers and writers wrap their body in `with self._lock:` and executor jobs hold the lock for the duration of their store operation, preventing interleaved cursor/row_factory corruption and lost writes. Verified by test_concurrent_loop_and_executor_writes_do_not_corrupt. |
| T-06.1-08-SC | Tampering | npm/pip/cargo installs | accept | No new packages installed — stdlib sqlite3 + threading only. No package-legitimacy gate required. |
