# Phase 06.1: Code Review Report

**Reviewed:** 2026-06-25
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

This phase wires the core live trade loop: the BarAggregator push handler, the
signal→risk→exec entry pipeline, the exit-fill→state/alert delivery rework
(`_place_exit_order` now returns `int` filled-qty), and the SAFE-03 steady-state
`reconcile_once` drift loop. The wiring of the async pipeline, the `_entries_enabled`
gate, the `_gateway` property/setter seam, and the dual-path `_on_bar_closed` bridge
are correct and defensible.

However, the safety-critical exit and reconciliation paths — the literal CORE VALUE of
this project ("a correct and safe automated trade loop") — contain three BLOCKER-class
defects that corrupt position quantity and leave live broker positions permanently
unmanaged. Two of them are masked by a test suite that stubs `manage_exit` to return
`0`, so the realistic non-zero-fill path is never exercised.

### Adjudication of the priority findings supplied in the brief

1. **"Stop-loss bypass / fail-open state drift" (manager.py) — REAL (BLOCKER, CR-01).**
   `_trigger_stop_out` persists `phase=CLOSED` DB-first (evaluate_close already set it),
   then calls `_place_exit_order`. If `manage_exit` returns `0` (order failed / no fill),
   the `if filled_qty > 0` block is skipped, so `remaining_quantity` stays > 0 while the
   in-memory phase is already CLOSED and the row stays in `manager._positions`. I traced
   `reconcile_once` end-to-end: it does **NOT** re-detect this. Its only two branches are
   "externally-closed" (code absent from broker_map — but here the broker still holds the
   position, so this is False) and "orphan" (code not in memory — but it IS in memory, so
   skipped). `reconcile_once` has no quantity-drift / CLOSED-but-held branch (that logic
   exists only in `startup_reconcile`, which runs once at boot). Result: a zero-fill
   stop-out leaves a live, stop-less broker position that `on_bar` ignores (phase CLOSED →
   early return) until the next process restart. The SAFE-03 loop does not mitigate it.

2. **"Type/signature mismatch — exit path TypeError" (manager.py) — FALSE POSITIVE.**
   `manage_exit` always returns an `int` (`total_filled` starts at 0 and only accumulates
   `int(...)` sums). Even if a mock returned `None`/`str`, `int(filled_qty)` at
   `_place_exit_order` line 877 is inside the `try` whose `except Exception` returns `0`
   (line 878-880), so no uncaught `TypeError` can reach a caller. `force_close_all`'s
   `filled < qty` compares two ints. No genuine TypeError path exists.

3. **Third finding (surfaced): double-decrement of `remaining_quantity` on partial profit
   (BLOCKER, CR-02)** and **orphan adoption never registered in-memory (BLOCKER, CR-03).**
   See findings below.

## Critical Issues

### CR-01: Zero-fill stop-out leaves a live, unmanaged broker position (fail-open stop-loss)

**File:** `bot/position/manager.py:682-696`, cross-referenced with `bot/gateway/gateway.py:803-863`
**Issue:**
`_trigger_stop_out` persists `phase=CLOSED` to the DB first (line 682; `evaluate_close`
already mutated `pos.phase = CLOSED` at `state.py:207`). It then calls `_place_exit_order`.
When `manage_exit` returns `0` (broker rejected the order, OpenD down, or no fill within
the escalation budget), the guarded block at lines 691-711 is skipped entirely:
`remaining_quantity` is never zeroed and stays > 0, the position object stays in
`manager._positions`, and its phase is permanently `CLOSED`. On the next bar,
`on_bar` returns early (`manager.py:206` — CLOSED short-circuits), so the stop is never
re-attempted.

`reconcile_once` cannot recover this state. Trace: the position's code is still in
`broker_map` (broker holds the shares), so the externally-closed branch
(`gateway.py:807 if code not in broker_map`) is False; it is in `state_codes`, so the
orphan branch (`gateway.py:830`) is skipped. There is no quantity-drift / "CLOSED in
memory but held at broker" branch in `reconcile_once` — that logic exists only in
`startup_reconcile` (`gateway.py:936-956`), which runs once at boot. The broker position
therefore remains live and stop-less until a full process restart. This defeats the
single most important safety guarantee of the system.

The existing tests do not catch this because `mock_engine.manage_exit` returns `0`
(`tests/position/test_manager.py:144`), which is exactly the failure case — yet the tests
assert only the alert/phase, not that a still-held position gets re-protected.

**Fix:** On a zero / short fill, do NOT leave the position CLOSED-but-held. Either keep it
in a managed phase so `on_bar` retries, or have `reconcile_once` detect
"in memory, in broker_map, but phase==CLOSED or stored remaining != broker qty" and
re-open/re-protect it. Minimum viable fix in `_trigger_stop_out`:
```python
filled_qty = await self._place_exit_order(pos.code, qty)
if filled_qty >= qty:
    pos.remaining_quantity = 0
    pos.phase = PositionPhase.CLOSED
    pos.updated_at = now_et()
    self._persist_position(pos, event="stop_out_filled")
    # ... fire alert ...
else:
    # Exit did NOT complete — revert the premature CLOSED so on_bar keeps
    # retrying the stop, and persist the still-open state DB-first.
    pos.remaining_quantity = max(0, pos.remaining_quantity - filled_qty)
    pos.phase = prev_phase if pos.remaining_quantity > 0 else PositionPhase.CLOSED
    pos.updated_at = now_et()
    self._persist_position(pos, event="stop_out_incomplete")
    _logger.error("stop_out_incomplete_position_still_held",
                  code=pos.code, requested=qty, filled=filled_qty,
                  remaining=pos.remaining_quantity)
```
Additionally, add a quantity-drift branch to `reconcile_once` (mirroring
`startup_reconcile` lines 936-956) so steady-state catches stored-qty ≠ broker-qty and
CLOSED-but-held positions, fires an alert, and re-arms management.

### CR-02: Double-decrement of `remaining_quantity` on partial profit understates the position

**File:** `bot/position/manager.py:597-603`
**Issue:**
The partial-profit path decrements `remaining_quantity` **twice** for a single scale-out.
`evaluate_close` already decrements it when it returns the PARTIAL action
(`state.py:214: self.remaining_quantity -= partial_qty`) and returns `partial_qty` as the
qty to sell. `_trigger_partial_profit` then sells that same `qty` via
`manage_exit(qty=partial_qty)` and, on a real fill, decrements **again**:
```python
filled_qty = await self._place_exit_order(pos.code, qty)   # qty == partial_qty
...
if filled_qty > 0:
    pos.remaining_quantity = max(0, pos.remaining_quantity - filled_qty)  # second decrement
```
Numeric trace (the project's own test scenario): ACTIVE, remaining=300, partial_qty=99.
`evaluate_close` sets remaining=201. `manage_exit` fills 99 and returns 99. Line 601 sets
remaining = `201 - 99 = 102`. The broker actually holds 201 shares; the bot now believes
it holds 102 — a 99-share phantom understatement. On the next stop-out the bot will only
try to exit 102 shares, leaving 99 shares live and unmanaged. The method's own docstring
is self-contradictory: line 576 says "evaluate_close() has already decremented
pos.remaining_quantity" while line 580 says "filled_qty … drives remaining_quantity
decrement."

This is masked in tests because `mock_engine.manage_exit` returns `0`
(`tests/position/test_manager.py:144`), so the `if filled_qty > 0` block never runs and
`test_close_at_0_75R_triggers_partial_profit` passes at 201. The realistic non-zero-fill
path is never exercised.

Note: the stop-out path (CR-01) does NOT have the double-decrement, because the STOP_OUT
branch of `evaluate_close` returns `remaining_quantity` *without* decrementing
(`state.py:208`). The two FSM actions have asymmetric decrement semantics, and the partial
handler wrongly assumes the stop-out semantics.

**Fix:** Do not decrement again in `_trigger_partial_profit`; `evaluate_close` already
applied the intended quantity. Instead, reconcile only on a *short* fill (broker filled
fewer than requested), and persist for audit:
```python
filled_qty = await self._place_exit_order(pos.code, qty)
# evaluate_close already removed `qty` from remaining_quantity. Only correct
# if the broker under-filled (filled_qty < qty) — add the shortfall back.
if 0 <= filled_qty < qty:
    shortfall = qty - filled_qty
    pos.remaining_quantity += shortfall
    _logger.warning("partial_short_fill", code=pos.code,
                    requested=qty, filled=filled_qty, restored=shortfall)
pos.updated_at = now_et()
self._persist_position(pos, event="partial_profit_filled")
```
Whatever the chosen convention, the partial and stop-out paths must agree on whether
`evaluate_close` or the handler owns the decrement — currently they disagree.

### CR-03: Mid-session orphan adoption is never registered in `manager._positions` — adopted positions go unmanaged

**File:** `bot/gateway/gateway.py:827-855`
**Issue:**
`reconcile_once`'s orphan branch (broker holds a position the bot doesn't know about)
inserts an ACTIVE row into the DB, subscribes the 5m feed, and audits `drift_orphan_adopted`
— but it never adds a `PositionState` to `manager._positions`. Unlike `startup_reconcile`
(which is always followed by `position_manager.reconstruct_from_store()` in
`_readiness_gate`, `bot.py:419`), `reconcile_once` runs in steady state with **no**
subsequent `reconstruct_from_store()`. The grep confirms only one in-memory write in the
file — the `del` at line 819 — and zero inserts into `_positions`.

Consequence: an orphan adopted mid-session (e.g. a manual broker-UI buy, or a fill that
arrived during a disconnect) gets a DB row and a live K_5M feed but is **invisible to
`on_bar`**. It receives no stop, no breakeven, no trail, and no exit until the next bot
restart reconstructs it from the DB. The plan explicitly promised "adopt-**and-protect**"
(`06.1-02-PLAN.md:14`); the protection half is missing. For a long-only intraday strategy
this means an unstopped position can ride into force-close (or overnight if force-close
also misses it) without risk management.

**Fix:** After the DB insert + subscribe, build the `PositionState` and register it in
memory so `on_bar` manages it the same cycle, e.g.:
```python
from bot.position.state import PositionState, PositionPhase
pos = PositionState(
    position_id=position_id, code=code, phase=PositionPhase.ACTIVE,
    entry_price=bp["avg_cost"], initial_stop=stop, trail_stop=stop,
    full_quantity=bp["qty"], remaining_quantity=bp["qty"],
    entry_order_id="", avg_fill_price=bp["avg_cost"],
    opened_at=now_et(), updated_at=now_et(),
)
manager._positions[code] = pos
```
(Or call a `manager.adopt_orphan(...)` helper so the in-memory/DB writes stay co-located
with the rest of the manager's invariants.)

## Warnings

### WR-01: Partial-profit handler never marks the position CLOSED when the last share is sold

**File:** `bot/position/manager.py:597-603`
**Issue:** Unlike `_trigger_stop_out` (lines 692-694 set `phase=CLOSED` when
`remaining_quantity` hits 0), `_trigger_partial_profit` only updates `remaining_quantity`
and persists with `event="partial_profit_filled"` — it never transitions to CLOSED even if
the (corrected) decrement drives remaining to 0. While a *partial* by definition leaves
shares open, an over-fill or a misconfigured `partial_profit_fraction` of 1.0 could zero
the position; it would then sit in `PARTIAL_TAKEN` with `remaining_quantity == 0` forever,
never closing and never firing the full-close exit alert path. Make the close transition
explicit and symmetric with the stop-out handler.

### WR-02: `manage_exit` retry-until-flat budget can be exhausted, but the caller treats any non-zero return as "applied" without checking for a short fill

**File:** `bot/position/manager.py:691-696` and `bot/execution/engine.py:378-448`
**Issue:** `manage_exit`'s `while remaining > 0` loop only terminates when fully flat OR
when the surrounding escalation logic gives up (e.g. an exception propagates out, caught by
`_place_exit_order` → returns 0). But a partial fill followed by a raised exception inside
the loop returns the partial `total_filled` via the `except` at `manager.py:878` returning
`0` — silently discarding the already-filled quantity count. The caller then believes
nothing filled, while shares were actually sold. Combined with CR-01, this widens the
window where the bot's view of `remaining_quantity` diverges from the broker. Recommend
`manage_exit` never raise past its own loop (return the partial `total_filled`), and have
`_place_exit_order` distinguish "raised after partial fill" from "zero fill."

### WR-03: Fire-and-forget drift-alert task is unreferenced and may be garbage-collected before sending

**File:** `bot/gateway/gateway.py:822-824`
**Issue:** `asyncio.create_task(alerter.send(...))` in the externally-closed branch is not
assigned to any variable and not tracked. Python may garbage-collect a bare task before it
runs to completion (documented asyncio footgun), silently dropping the DRIFT alert — the
one signal that tells the operator a position was closed out from under the bot. The same
pattern recurs in `bot.py` (`_job_eod_report:602`, `_shutdown`-adjacent sends) and the
`main.py` alert lambdas. At minimum, keep a reference set on the gateway/bot
(`self._bg_tasks.add(t); t.add_done_callback(self._bg_tasks.discard)`).

### WR-04: `reconcile_once` orphan adoption uses `INSERT OR IGNORE` and silently no-ops on `position_id` collisions / pre-existing rows

**File:** `bot/gateway/gateway.py:839-848` (and the same pattern in `startup_reconcile:980-997`)
**Issue:** `INSERT OR IGNORE` means that if a CLOSED row for `code` (or any row colliding on
a UNIQUE constraint) already exists, the adoption silently does nothing — no row inserted,
no error, but the audit log still records `drift_orphan_adopted` as if it succeeded. A
re-adopted symbol (closed earlier in the day, re-bought manually) would be audited as
adopted while no ACTIVE row exists, leaving the broker position unmanaged and the operator
falsely reassured. Verify the table's uniqueness constraints and use an explicit
upsert/branch, or check `cursor.rowcount` and log when the IGNORE path is taken.

## Info

### IN-01: Dead local variable `now_time` in `force_close_all`

**Issue:** `now_time = now.timetz().replace(tzinfo=None).replace(microsecond=0)` is computed

**Fix:** Delete line 324.

### IN-02: `_on_bar_closed` dual sync/async path is correct but fragile and under-commented for the deadlock risk

**File:** `bot/service/bot.py:212-225`
**Issue:** The production path relies on `asyncio.get_running_loop()` raising `RuntimeError`
when invoked from the SDK push thread (so it returns the coroutine for
`run_coroutine_threadsafe`). This is correct given `BarAggregator` calls
`run_coroutine_threadsafe(self._on_bar_closed(bar_data), self._loop)` from the SDK thread
(`bar_aggregator.py:311`). It is, however, a non-obvious invariant: if a future refactor
ever calls `_on_bar_closed` and then passes its result to `run_coroutine_threadsafe`
*from the loop thread*, the `create_task` branch would schedule on the wrong loop. Add an
assertion/comment binding this method's contract to "must be invoked synchronously inside
`run_coroutine_threadsafe` from a non-loop thread in production."

### IN-03: `_gateway` setter re-registers the handler only when `_bar_agg` is set — production never exercises the setter, so the test-only seam adds surface area

**File:** `bot/service/bot.py:131-143`
**Issue:** In production the gateway is supplied via `__init__` (`self.__gateway = gateway`,
line 93 — direct field write, bypassing the property setter), so the setter's
`set_handler` re-registration only ever fires in tests that reassign `bot._gateway`. There
is no double-registration in production (`_do_startup_wiring` registers directly on
`self.__gateway` at line 166, bypassing the property). The seam is correct but exists solely
for a test fixture; consider documenting it as test-only or exposing an explicit
`rebind_gateway()` to avoid a subtle stale-handler bug if someone later assigns
`self._gateway = ...` inside `__init__` (which would route through the setter while
`_bar_agg` is None and silently skip registration).
