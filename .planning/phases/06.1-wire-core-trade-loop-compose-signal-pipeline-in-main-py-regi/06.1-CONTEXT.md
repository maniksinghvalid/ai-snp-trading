# Phase 06.1: Wire core trade loop - Context

**Gathered:** 2026-06-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Connect the already-built, unit-tested Phase 1–5 components into a functioning end-to-end
live trade loop in `bot/main.py` / `TradingBot`. Every component exists and passes in isolation;
the cross-phase **composition layer was never built** (`.planning/v1.0-MILESTONE-AUDIT.md`).

This phase delivers the wiring identified by the v1.0 milestone audit punch-list:
1. Compose the signal pipeline: `BarAggregator → SignalEngine → RiskEngine → ExecutionEngine → PositionManager`.
2. Register the K_5M push handler so subscribed 5m bars have a consumer (`gateway.set_handler()`).
3. Gate order submission on `_entries_enabled` (make the write-only flag enforceable — SVC-02/D-09).
4. Start the SAFE-03 steady-state reconciliation loop as a task **and** implement `reconcile_once()` drift logic.
5. Fix the exit-fill → alert/state delivery path (EXEC-05/ALERT-02/WARNING-01).
6. Pass `bar_buffer` to `PositionManager` so the POS-03 swing-low trail works (WARNING-02).

**In scope:** the composition/wiring only — the leaf components are not redesigned.

**Out of scope (explicit — separate remediation steps per the audit):**
- Live SIMULATE UAT (audit step 2) — closes the Phase 01/03/04 `human_needed` verifications.
- Phase 6 Backtester (BT-01..04, audit step 3) — its own phase.

<decisions>
## Implementation Decisions

### Exit-fill → alert & state delivery (WARNING-01 / ALERT-02 / EXEC-05)
- **D-01:** Drive exit state transitions and exit alerts **synchronously from `engine.manage_exit()`'s
  return value**, not from the async `exit_order_id` push-match path. `manage_exit()` is a blocking
  retry-until-flat loop that polls its own fills and returns total filled-qty (an `int`), and places
  multiple cancel-replace orders internally (no single exit order_id). After it returns, `PositionManager`
  applies the exit (decrement `remaining_quantity`, run the FSM transition) and fires `on_exit_alert(code, reason, r)`
  directly from that return value.
- **D-02:** Retire reliance on `exit_order_id` / `_find_position_by_exit_order_id` / `_on_exit_fill`
  for **exit-alert delivery**. All exits in this architecture are bot-initiated (D-01 synthetic
  bot-monitored stop — no resting broker stop orders on SIMULATE), so every exit flows through
  `manage_exit()`. `_place_exit_order()` must stop returning `None` and instead surface the filled-qty
  so the manager can apply + alert. (Rationale also covers unreliable SIMULATE push delivery — poll-based.)

### Composition seam & construction order
- **D-03:** Compose the pipeline **inside `TradingBot`**, not `main.py`. The forcing constraint:
  `BarAggregator` needs the *running* asyncio loop and `PositionManager` needs `BarAggregator._bar_buffer`,
  but `main.py` builds everything before `asyncio.run()`.
- **D-04:** `main.py` stays **pure DI** — it builds the leaf components (including the **new**
  `SignalEngine` and `RiskEngine` instantiations, which are loop-independent) and injects them into `TradingBot`.
- **D-05:** In `TradingBot.run()` (loop live): construct `BarAggregator(get_running_loop(), self._on_bar_closed)`;
  own the `_on_bar_closed` orchestration method (signal→risk→exec, reads `_entries_enabled`); register it via
  `gateway.set_handler(...)`; and **late-bind** `bar_buffer` into `PositionManager`
  (`self._position_manager._bar_buffer = self._bar_agg._bar_buffer`). Only `BarAggregator` needs the loop.

### `_entries_enabled` gate (SVC-02 / D-09)
- **D-06:** The flag gates **the entry branch only**, inside `_on_bar_closed`. Position-management runs
  on every closed bar regardless (`await position_manager.process_bar(bar)` for trail/partial/stop). The
  `signal → risk → consume_intent` entry branch runs **only when `_entries_enabled` is True**. This is
  entry-only by construction (exits/management never flow through the gate) and avoids spurious
  `OrderIntent` persistence / daily-tally increment while entries are paused.

### `reconcile_once()` drift logic (SAFE-03)
- **D-07:** Implement **broker-truth-wins + alert**, reusing `startup_reconcile`'s broker-truth core
  (do not leave the no-op `drift:{}` skeleton). Each 60–90s cycle diffs broker positions vs in-memory:
  - Externally-closed (in memory, gone from broker, **and no in-flight exit order**) → mark `CLOSED`,
    stop managing, fire a Telegram alert. This is the specific bug the audit calls out (manual broker-UI
    close undetected until restart).
  - Orphan (in broker, not in memory) → adopt-and-protect (same policy as startup).
  - **Skip** positions with an active `manage_exit` in flight to avoid racing live FSM transitions.
- **D-08:** Start `gateway.reconciliation_loop()` as an `asyncio.create_task(...)` in `TradingBot.run()`
  (alongside the watchdog task), cadence within SAFE-03's 60–90s window (existing `interval_s=75.0` default).

### Claude's Discretion (mechanical wiring — planner/executor)
- Exact placement of `gateway.set_handler()` (at startup vs in the market-open subscribe job) — keep
  the handler registered for the session; respect `BarAggregator.reset_session()` semantics (do NOT reset
  the `_seen_time_keys` dedup set on reconnect, only on a genuinely new trading session).
- Threading the filled-qty return through `_place_exit_order` → both call sites (partial @line ~569 and
  force-close @line ~660 in `manager.py`).
- The precise `_on_bar_closed` signature / BarEvent construction from the `bar_data` dict.
- Whether `reconcile_once`'s diff logic lives in the gateway or a shared helper reused by `startup_reconcile`.

</decisions>

## Existing Code Insights

### Reusable Assets
- `startup_reconcile(store, manager)` — broker-truth-wins reconciliation core; reuse for `reconcile_once()` drift logic (D-07).
- `BarAggregator` — fully built `CurKlineHandlerBase` subclass with SDK-thread→asyncio bridge, HOD/LOD, `_bar_buffer` deque, reconnect dedup. Just needs construction (with running loop) + `set_handler` registration.
- `engine.manage_exit(...) -> int` — already retry-until-flat and polls its own fills; its return value is the authoritative exit-qty source for D-01.
- `OpenDWatchdog` — already toggles `bot._entries_enabled`; D-06 makes that toggle finally effective.

### Established Patterns
- `main.py` is pure DI; loop-dependent objects must be built where the loop runs (TradingBot.run()) — D-03/D-05.
- Fire-and-forget alerts via `asyncio.create_task` lambdas (ALERT-04) — exit alert in D-01 reuses the existing `on_exit_alert` callback already wired in `main.py`.
- Async tasks (watchdog) launched via `asyncio.create_task` in `run()` — reconciliation loop mirrors this (D-08).

### Integration Points
- `gateway.subscribe()` ↔ `BarAggregator` via `set_handler()` (the missing link — BLOCKER-01).
- `BarAggregator._bar_buffer` ↔ `PositionManager._bar_buffer` via late-bind (WARNING-02 / POS-03).
- `TradingBot._entries_enabled` ↔ `_on_bar_closed` entry branch (BLOCKER-02 — the read site).
- `manage_exit()` return ↔ `PositionManager` exit-apply + `on_exit_alert` (WARNING-01).

<specifics>
## Specific Ideas

The v1.0 audit's remediation step 1 is the exact spec for this phase — its BLOCKER/WARNING list maps
1:1 to D-01..D-08. The design tension the user resolved: `manage_exit()` returns a filled-qty `int`
(not an `order_id`) and places N cancel-replace orders internally, so the audit's literal "set
`exit_order_id`" wording is superseded by the synchronous-return approach (D-01/D-02).
