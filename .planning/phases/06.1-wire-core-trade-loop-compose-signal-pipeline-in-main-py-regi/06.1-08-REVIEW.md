# Phase 06.1-08: Code Review Report

**Reviewed:** 2026-06-25
**Depth:** standard
**Files Reviewed:** 3
**Status:** issues_found

## Summary

This gap-closure changed `StateStore` to open SQLite with `check_same_thread=False`,
added a `threading.RLock` exposed via `lock()`, wrapped the three store accessor methods
(`upsert_position`, `get_closed_trades`, `get_open_positions`) in `with self._lock:`, and
made the four `run_in_executor` jobs in `bot.py` acquire `self._store.lock()` on the worker
thread.

The narrow `check_same_thread=False` change does fix the *crash* (`sqlite3.ProgrammingError`)
the UAT reported — a worker thread can now touch the connection at all. That much is correct.

However, the lock that is supposed to make that safe is **only acquired by the four jobs in
bot.py and the three accessor methods in store.py**. Every other concurrent writer/reader of
the same shared connection — the SAFE-03 `reconciliation_loop`, `signal_engine`,
`risk_engine`, `execution_engine`, and `position_manager` — touches `store.conn` directly and
holds no lock. Because the reconcile loop runs on the event-loop thread and `await`s mid-write
(allowing a lock-holding worker job to run concurrently on a worker thread against the *same*
connection), the lock provides effectively zero mutual exclusion for the most dangerous paths.
The fix removed the safety net (`check_same_thread`) but did not replace it with the
serialization it claims to. This is a BLOCKER: the original crash is converted into silent
data races / `row_factory` corruption / interleaved writes on a single shared connection.

The regression test passes but does not actually exercise the cross-thread *contention*
scenario it documents (it only runs reads from worker threads; never a concurrent event-loop
writer), so it gives false confidence.

## Critical Issues

### CR-01: Lock does not cover the reconciliation loop or any engine/manager writer — races against locked worker jobs on the same connection

**File:** `bot/state/store.py:204` (the `check_same_thread=False`), `bot/gateway/gateway.py:840-1133` (unlocked writers), `bot/service/bot.py:171-176` (reconcile task on event loop)

**Issue:**
The fix's stated contract (store.py:161-164, 241-258) is: "RLock serializes ALL connection
access across threads" and "Executor jobs must acquire this lock around ALL store access so
that worker-thread operations are serialized against event-loop-thread manager/engine writes."

That contract is not met. A grep for `.lock()` shows the ONLY acquirers are the four jobs in
`bot.py` (lines 452, 492, 538, 606) and the three accessors inside store.py. Meanwhile the
following all access the shared `store.conn` with **no lock**:

- `bot/gateway/gateway.py:840-926, 1122, 1129-1133` — `reconcile_once`: executes UPDATE/INSERT,
  commits, and flips `store.conn.row_factory = sqlite3.Row` then back to `None`.
- `bot/position/manager.py:965-973, 998-1003` — `_increment_daily_filled_count`,
  `_resolve_pending_intent`.
- `bot/risk/risk_engine.py:161-174`, `bot/execution/engine.py:462-467`,
  `bot/signal/signal_engine.py:267,286,346` — execute/commit on `store.conn`.

`reconciliation_loop` is started as `self._reconcile_task` on the event loop (bot.py:171-178)
and `reconcile_once` performs `await self._derive_lod_for_orphan(...)` / `await self.subscribe(...)`
(gateway.py:907, 1115) **interleaved** with `store.conn.execute` / `store.conn.row_factory`
mutation. Each `await` yields the event loop, and a worker job that has acquired
`self._store.lock()` will then run its `conn.execute`/`row_factory` work concurrently on a
worker thread against the *same* connection. The worker holds the RLock; the reconcile loop
does not even try to take it. Result: concurrent use of one `sqlite3.Connection` and concurrent
`row_factory` mutation — exactly the corruption the lock was added to prevent, now with the
`check_same_thread` guard removed so it no longer raises but silently misbehaves (wrong
`row_factory` observed mid-fetch -> `dict(r)` on a tuple -> wrong/garbled startup
reconciliation, or `sqlite3.ProgrammingError: recursive use of cursors`).

This is the central defect of the gap-closure: the crash is masked, the underlying unsafe
concurrent access is not actually serialized.

**Fix:**
The lock must guard *every* path that touches the shared connection, not just the four jobs.
Two viable approaches:

1. Push the lock down into the connection access itself so callers cannot forget it. Have all
   DB work go through `StateStore` methods that each `with self._lock:`, and stop exposing the
   raw `conn`. Then no caller needs to know about the lock.

2. If the raw-`conn` pattern must stay, make `reconciliation_loop` / `reconcile_once` and the
   engine/manager writers acquire `store.lock()` around each connection touch — and critically,
   the lock must NOT be held across an `await` (see CR-02). Restructure `reconcile_once` so each
   DB mutation is a short `with store.lock(): conn.execute(...); conn.commit()` block with no
   `await` inside the locked region.

Until one of these is done, the WAL pragma + `check_same_thread=False` simply trades a loud
crash for silent corruption.

### CR-02: RLock is a thread lock held across `await` points — does not serialize event-loop-thread access and risks cross-thread deadlock under contention

**File:** `bot/state/store.py:164,241-258`; `bot/service/bot.py:171-176`, `bot/gateway/gateway.py:907,1115`

**Issue:**
`threading.RLock` provides mutual exclusion *between threads* and re-entrancy *within the same
thread*. It does nothing to serialize two coroutines on the same event-loop thread, and it is
dangerous when a coroutine holds it across an `await`.

Even if CR-01 is addressed by wrapping the reconcile loop in `store.lock()`, doing so naively
(`with store.lock(): ... await ...`) means the **event-loop thread** holds the RLock while
suspended at an `await`. A worker job then calls `loop.run_in_executor(...)` whose body does
`with self._store.lock():` on a worker thread and blocks. Because the RLock is owned by the
event-loop thread (a *different* thread), the worker blocks the executor; the event loop may
then be waiting (directly or transitively) on that executor result while still owning the lock
— a classic lock-held-across-await deadlock that an RLock cannot rescue (re-entrancy only helps
the *same* thread re-acquire).

This is a latent BLOCKER because the current code happens not to lock the reconcile loop at all
(CR-01), so it does not deadlock today — it corrupts instead. Any correct fix for CR-01 that
naively wraps the awaiting reconcile path in `store.lock()` will introduce this deadlock.

**Fix:**
Never hold the store lock across an `await`. Decompose each event-loop DB operation so the lock
covers only the synchronous `conn.execute(...); conn.commit()` (and any `row_factory`
flip/reset) with no `await` inside the `with store.lock():` block. For example, in
`reconcile_once` move the broker I/O (`await self.subscribe`, `await self._derive_lod_for_orphan`)
outside the locked region and only re-acquire the lock for the bare DB write. Document this
invariant in `store.lock()`'s docstring ("the returned lock MUST NOT be held across an await").

## Warnings

### WR-01: Regression test never exercises concurrent event-loop-thread access — it cannot detect the actual race

**File:** `tests/state/test_store_threadsafety.py:123-179`

**Issue:**
`test_concurrent_loop_and_executor_writes_do_not_corrupt` is named for the loop-vs-executor race
but only schedules `2*N` `get_open_positions()` calls, all via `loop.run_in_executor(...)` —
i.e. all on worker threads, all read-only, all routed through the RLock-guarded accessor. It
never issues a concurrent write on the event-loop thread (no `store.upsert_position` /
`conn.execute` / reconcile-style mutation awaited on the loop while a worker holds the lock).
Because of that, the test would pass even if the reconcile loop's unlocked writes (CR-01) were
racing — it does not touch that path at all. The test asserts only `isinstance(r, list)`, which
the default-`row_factory` tuple path would still satisfy in many corruption cases. It is GREEN
but proves only "the crash is gone," not "concurrent access is serialized."

**Fix:**
Add a test that, while N executor reads are in flight, also drives a writer on the event-loop
thread (e.g. `store.upsert_position(...)` and a `row_factory`-flipping read in the same loop),
mirroring the reconcile loop. Better: a stress test that runs an event-loop coroutine doing
repeated `row_factory` flips + writes concurrently with executor reads and asserts no
`ProgrammingError`/`recursive use of cursors` and that read results have the expected `dict`
shape. This is the scenario CR-01 describes and the only one that would have caught the gap.

### WR-02: `lock()` returns the raw RLock but the docstring/usage implies a context-manager factory — fragile and easy to misuse

**File:** `bot/state/store.py:241-258`

**Issue:**
`lock()` returns `self._lock` (the RLock object), and callers do `with self._store.lock():`.
This works because RLock is itself a context manager, but the method name + docstring ("Return
the store's re-entrant lock as a context manager") invites a caller to write
`lock = store.lock(); with lock: ...` or to call it once and reuse — and more importantly it
leaks the raw lock so any caller can `lock().acquire()` without releasing, or hold it across an
await (CR-02). Returning the bare primitive defeats the encapsulation the method seems intended
to provide.

**Fix:**
Either rename to make the intent unambiguous (e.g. keep returning the RLock but document
"returns the underlying RLock; use only as `with store.lock():`"), or return a dedicated
context manager that asserts it is not entered on the event-loop thread / not re-entered across
an await. Combined with CR-01, the cleaner resolution is to not expose the lock at all and route
all access through guarded `StateStore` methods.

### WR-03: WAL `journal_mode` is set but `busy_timeout` is not — concurrent writers can raise `database is locked`

**File:** `bot/state/store.py:206`

**Issue:**
`PRAGMA journal_mode=WAL` is enabled to "improve concurrency," but with a single shared
connection and `check_same_thread=False`, the real concurrency concern is SQLite's internal
write lock. Under WAL, a write while another write/checkpoint holds the lock returns
`sqlite3.OperationalError: database is locked` immediately (default `busy_timeout=0`). Once
CR-01/CR-02 are fixed so multiple threads legitimately contend for the connection, the absence
of a `busy_timeout` means transient lock contention surfaces as exceptions rather than a short
wait. The job-level `except Exception` handlers (bot.py:465, 503, 552, 632) will swallow these
as generic errors, silently dropping a scan/report write.

**Fix:**
Set a busy timeout right after connect, e.g. `self._conn.execute("PRAGMA busy_timeout=5000")`
(or `sqlite3.connect(..., timeout=5.0)`), so contended writes wait briefly instead of raising.
Note this is defense-in-depth; it does not substitute for the serialization required by CR-01.

## Info

### IN-01: `check_same_thread=False` safety comment overstates the guarantee

**File:** `bot/state/store.py:200-204`

**Issue:**
The comment states "All access is serialized by self._lock so concurrent use is safe." As
documented in CR-01, that is not true for the reconcile loop / engines / manager which never
acquire the lock. A future maintainer reading this comment will reasonably assume the
invariant holds and add another unlocked `conn` caller. The comment encodes an invariant the
code does not enforce.

**Fix:**
Until the lock genuinely covers all paths, soften the comment to reflect reality (e.g. "Callers
MUST acquire self._lock around every connection access; this is enforced by convention, not by
the type system — see CR-01") or, preferably, make the comment true by implementing CR-01.
