# Phase 06.1 Plan 08: StateStore Thread-Safety (SQLite cross-thread UAT blocker) Summary

Closes the single remaining UAT blocker for Phase 06.1: `sqlite3.ProgrammingError: SQLite objects
created in a thread can only be used in that same thread`. The StateStore connection was opened
with the default `check_same_thread=True`, binding it to the main thread. All four scheduled jobs
in `bot/service/bot.py` passed `self._store` into `loop.run_in_executor(None, ...)` worker threads
where `conn.execute` / `row_factory` access raised `ProgrammingError`.

**Fix:** `check_same_thread=False` (connection usable cross-thread) + `threading.RLock` (serializes
all connection access) + lock-wrapping of all four executor jobs and the three store methods that
mutate shared connection state.

## What Was Built

### bot/state/store.py (thread-safe StateStore)

- `threading` imported at module level.
- `StateStore.__init__` creates `self._lock = threading.RLock()`.
- `StateStore.open()` opens with `sqlite3.connect(self._db_path, check_same_thread=False)`.
- New public `lock()` method returns `self._lock` (usable as `with store.lock(): ...`).
- `upsert_position`, `get_closed_trades`, `get_open_positions` each wrapped in `with self._lock:`
  so the row_factory flip + fetch + reset sequence is atomic.

### bot/service/bot.py (lock-wrapped executor jobs)

All four `run_in_executor` jobs acquire `with self._store.lock():` INSIDE the worker function
(on the thread that actually uses the connection):

- `_job_premarket_scan`: worker function `_premarket_scan_worker` wraps `run_daily_scan`.
- `_job_market_open_subscribe`: worker function `_get_watchlist_worker` wraps the store read.
- `_job_intraday_rescan`: worker function `_intraday_rescan_worker` wraps `run_intraday_rescan`.
- `_job_eod_report`: `_fetch_build_write` closure acquires lock around `get_closed_trades` + `get_open_positions`.

### tests/state/test_store_threadsafety.py (RED-first regression tests)

Three tests that were RED (ProgrammingError) before the fix, GREEN after:

1. `test_store_write_through_executor_thread_succeeds` — write to `daily_trade_count` via run_in_executor then read back; asserts result == 3.
2. `test_store_read_through_executor_thread_succeeds` — call `get_open_positions()` via run_in_executor; asserts returns a list.
3. `test_concurrent_loop_and_executor_writes_do_not_corrupt` — N concurrent `get_open_positions()` calls from multiple executor threads; asserts all return list (no row_factory corruption).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Third regression test revised from direct-conn-execute to get_open_positions concurrent reads**

- **Found during:** Task 1 / Task 2 GREEN phase
- **Issue:** The original design for the third test used direct `store.conn.execute` from multiple workers without locking. After the fix, `check_same_thread=False` allows cross-thread access but concurrent `conn.execute` + `conn.commit()` without locking causes `SystemError: error return without exception set` in Python 3.14's CPython SQLite implementation — the unprotected concurrent writes corrupt internal cursor state. This is the exact T-06.1-08-02 race the plan warned about.
- **Fix:** Revised the third test to use `store.get_open_positions()` (the lock-protected public API) concurrently from N executor threads. This correctly verifies that the RLock serializes the row_factory flip + fetch + reset sequence (the concurrency hazard identified in the plan). The RED gate fires correctly via `ProgrammingError` (the conn.row_factory = sqlite3.Row access raises ProgrammingError on a worker thread with check_same_thread=True before the fix).
- **Files modified:** tests/state/test_store_threadsafety.py
- **Commit:** c670b0b (test revision bundled into GREEN commit)
