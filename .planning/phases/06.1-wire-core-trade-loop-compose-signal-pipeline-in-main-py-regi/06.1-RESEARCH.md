## Summary

Phase 06.1 is a pure composition/wiring phase. All six leaf components (BarAggregator, SignalEngine, RiskEngine, ExecutionEngine, PositionManager, MoomooGateway) exist, are fully implemented, and pass 405 unit tests in isolation. The cross-phase integration layer that connects them was never built.

The v1.0 milestone audit identified three hard blockers and two compounding warnings. This research confirms all five defects by direct code inspection and documents the exact signatures, attribute names, and method call sequences needed to wire them correctly.

The most important research finding is the **exit-fill delivery design conflict**: `_place_exit_order()` in `manager.py` currently calls `engine.manage_exit()` as fire-and-forget and returns `None` (line 843: `return None`). The docstring even acknowledges this: "Note: manage_exit returns total filled qty, not an order_id." The D-01/D-02 decision resolves this by making `_place_exit_order()` return the filled-qty `int` from `manage_exit()`, which callers then use directly to apply the exit and fire the alert — eliminating the broken `exit_order_id` push-match path entirely.

**Primary recommendation:** Wire the six seams in a single integration phase: (1) add set_handler to gateway.subscribe; (2) build BarAggregator + _on_bar_closed in TradingBot.run(); (3) add _entries_enabled read gate; (4) implement reconcile_once() drift logic and start reconciliation_loop as a task; (5) fix _place_exit_order to return filled-qty and thread it through both call sites; (6) late-bind bar_buffer into PositionManager. Then write a single integration test that drives a fake BarAggregator → SignalEngine → RiskEngine → ExecutionEngine → PositionManager pipeline end-to-end.

### Pattern 1: BarAggregator construction in TradingBot.run() (D-05)

The forcing constraint: `asyncio.get_running_loop()` is only available after `asyncio.run()` has started the event loop. `TradingBot.run()` is the first coroutine on that loop, so BarAggregator must be built there — not in `main.py`.

```python
# In TradingBot.run(), immediately after _readiness_gate():
loop = asyncio.get_running_loop()
self._bar_agg = BarAggregator(loop, self._on_bar_closed)
self._gateway.set_handler(self._bar_agg)
# Late-bind bar_buffer (WARNING-02 / POS-03)
self._position_manager._bar_buffer = self._bar_agg._bar_buffer
```

The `set_handler()` call is a method on `OpenQuoteContext` — confirmed by `skills/moomooapi/scripts/subscribe/push_kline.py` line 98:
```python
ctx.set_handler(handler)   # handler is a CurKlineHandlerBase subclass
```

`MoomooGateway` must expose this as a thin wrapper so the gateway encapsulates the quote_ctx:
```python
def set_handler(self, handler) -> None:
    """Register a CurKlineHandlerBase push handler on the quote context."""
    self._quote_ctx.set_handler(handler)
```

This method does NOT currently exist on `MoomooGateway` — it must be added.

### Pattern 2: _on_bar_closed signature and BarEvent construction (D-05)

`BarAggregator._on_bar_closed` receives a `bar_data: dict` (confirmed from `bar_aggregator.py` lines 289-299). The dict has exactly these keys:
```python
bar_data = {
    "code": str,       # Moomoo-format code e.g. "US.AAPL"
    "time_key": str,   # ISO-8601 closed bar timestamp
    "open": float,
    "high": float,
    "low": float,
    "close": float,
    "volume": int,
    "hod": float,      # session running max EXCLUDING bar B's first tick
    "lod": float,      # session running min EXCLUDING bar B's first tick
}
```

`TradingBot._on_bar_closed` must be an `async def` coroutine with signature `async def _on_bar_closed(self, bar_data: dict) -> None`.

BarEvent construction from bar_data (all keys map 1:1 to BarEvent fields):
```python
from bot.signal.events import BarEvent

async def _on_bar_closed(self, bar_data: dict) -> None:
    bar = BarEvent(
        code=bar_data["code"],
        time_key=bar_data["time_key"],
        open=bar_data["open"],
        high=bar_data["high"],
        low=bar_data["low"],
        close=bar_data["close"],
        volume=bar_data["volume"],
        hod=bar_data["hod"],
        lod=bar_data["lod"],
    )
    # Management always runs (D-06)
    await self._position_manager.on_bar(bar)
    # Entry branch only when enabled (D-06 gate)
    if not self._entries_enabled:
        return
    signal = await self._signal_engine.on_bar(bar)
    if signal is None:
        return
    intent = await self._risk_engine.on_signal(signal)
    if intent is None:
        return
    await self._execution_engine.consume_intent(intent)
```

Note: `PositionManager.on_bar()` accepts a `bar` argument with `.code` and `.close` attributes. The current signature is `async def on_bar(self, bar) -> None` — it accesses `bar.code`, `bar.close`, and `bar.time_key`. All are present on BarEvent.

### Pattern 3: _entries_enabled read gate (BLOCKER-02 / D-06)

Current state: `TradingBot._entries_enabled` is written in three places:
- `_readiness_gate()`: set True after startup reconcile (line 250)
- `OpenDWatchdog`: set False on disconnect (watchdog.py line 129); set True on reconnect (line 223)

**It is read nowhere.** The gate is never consulted before order submission.

The fix: the read site is in `_on_bar_closed`, after `position_manager.on_bar(bar)` completes. The flag gates the `signal → risk → consume_intent` branch only — management always runs regardless of `_entries_enabled`. This is correct by construction: exits never flow through the entry branch.

### Pattern 4: set_handler timing — at startup vs at market-open subscribe

**Recommendation (Claude's discretion):** Register the handler once at startup in `TradingBot.run()`, immediately after constructing `BarAggregator`. Do NOT re-register it inside `_job_market_open_subscribe`. Reasons:

1. `_job_market_open_subscribe` is a cron job that fires once at market open. If OpenD reconnects mid-session, `_readiness_gate` is re-run by the watchdog but `_job_market_open_subscribe` is NOT re-fired. The handler must survive reconnects.
2. `gateway.set_handler(handler)` is idempotent — calling it twice with the same handler is harmless but unnecessary.
3. `BarAggregator.reset_session()` — per its docstring: "DO NOT call on SDK reconnect — the `_seen_time_keys` dedup set must survive reconnects." Call `reset_session()` only at genuine session start (market open), never on reconnect. The natural call site is inside `_job_market_open_subscribe` before subscribing codes — but `set_handler()` call must remain at startup.

### Pattern 5: main.py gains SignalEngine and RiskEngine (D-04)

`SignalEngine` and `RiskEngine` constructors do NOT require the running loop:
- `SignalEngine(cfg, gateway, store)` — pure Python, no asyncio primitives at construction time
- `RiskEngine(cfg, gateway, store, signal_engine=None)` — same

These are loop-independent and must be built in `main.py` (per D-04) and injected into `TradingBot`. `TradingBot.__init__` must accept `signal_engine` and `risk_engine` as new constructor parameters alongside the existing ones.

```python
# main.py — new additions after step 5a:
signal_engine = SignalEngine(cfg=cfg, gateway=gateway, store=store)
risk_engine = RiskEngine(cfg=cfg, gateway=gateway, store=store, signal_engine=signal_engine)

# TradingBot constructor gains two new params:
bot = TradingBot(
    ...
    signal_engine=signal_engine,
    risk_engine=risk_engine,
)
```

### Pattern 6: reconcile_once() drift logic (D-07)

The current `reconcile_once()` is a no-op stub (gateway.py lines 750-770). It reads broker positions but returns `{"drift": {}}` without acting on any differences.

The D-07 logic reuses the diff core already written in `startup_reconcile()`:
- **Externally-closed** (in `_positions` memory, gone from broker, AND no `manage_exit` in flight): mark CLOSED, stop managing, fire Telegram alert via `asyncio.create_task(alerter.send(...))`.
- **Orphan** (in broker, not in `_positions`): adopt-and-protect — same logic as `startup_reconcile` Step 4.
- **Skip** positions with active `manage_exit` in flight: the `manage_exit()` loop is currently running on the asyncio event loop; `reconcile_once()` also runs on the same loop (no concurrent access to `_positions`). A position whose `pos.phase == CLOSED` but `remaining_quantity > 0` after a partial exit represents an in-flight exit — skip it.

The "in-flight manage_exit" detection heuristic: check `pos.exit_order_id is not None` and `pos.phase != PositionPhase.CLOSED`. If a stop-out was triggered and manage_exit is running, the position has a non-None `exit_order_id` and is not yet CLOSED. Skip those.

**Where does the diff logic live?** The planner may put it directly in `reconcile_once()` or extract a `_diff_broker_state(broker_map, manager)` helper that both `startup_reconcile` and `reconcile_once` call. Either is acceptable; the key constraint is that `reconcile_once()` must accept `store` and `manager` as parameters (or access them via `self._store` and `self._manager` if stored on the gateway). Current gateway constructor only takes `cfg`; injecting `store` and `manager` at `reconciliation_loop` call time (passed as args) is the cleanest approach without restructuring the gateway.

The `reconciliation_loop()` start call in `TradingBot.run()` (mirrors the watchdog task):
```python
self._reconcile_task = asyncio.create_task(
    self._gateway.reconciliation_loop(
        store=self._store,
        manager=self._position_manager,
        alerter=self._alerter,
    )
)
```

`reconciliation_loop()` must pass these through to `reconcile_once()`. The current signature `async def reconciliation_loop(self, interval_s: float = 75.0)` needs to gain `store`, `manager`, and `alerter` parameters.

### Pattern 7: Exit-fill → alert delivery fix (D-01/D-02 / WARNING-01)

**Current broken path:**
```
_trigger_stop_out → _place_exit_order → manage_exit() [fire-and-forget, ignores return]
                                         returns None
```
`pos.exit_order_id` is set to `None` (from `_place_exit_order` returning `None`), so `_find_position_by_exit_order_id()` never matches an exit fill, so `_on_exit_fill()` never fires, so `on_exit_alert()` is never called.

**Fixed path (D-01/D-02):**
```python
# _place_exit_order returns int (total filled qty)
async def _place_exit_order(self, code: str, qty: int) -> int:
    filled_qty = await self._engine.manage_exit(
        code=code,
        qty=qty,
        side=sell_side,
        escalation_step=self._cfg.exit_escalation_step_usd,
        escalation_cadence=self._cfg.exit_escalation_cadence_seconds,
        ttl=self._cfg.exit_ttl_seconds,
    )
    return filled_qty  # int, not None
```

Both call sites in manager.py must be updated to use the returned filled_qty:

**Call site 1 — `_trigger_partial_profit` (around line 569):**
```python
# Current (broken):
order_id = await self._place_exit_order(pos.code, qty)
if order_id:
    pos.exit_order_id = order_id

# Fixed (D-01):
filled_qty = await self._place_exit_order(pos.code, qty)
if filled_qty > 0:
    pos.remaining_quantity = max(0, pos.remaining_quantity - filled_qty)
    pos.updated_at = now_et()
    self._persist_position(pos, event="partial_profit_filled")
    # on_exit_alert already fired at trigger point in _trigger_partial_profit
    # (the existing alert block at lines 585-598 is already correct; keep it)
```

**Call site 2 — `_trigger_stop_out` (around line 660):**
```python
# Current (broken):
order_id = await self._place_exit_order(pos.code, qty)
if order_id:
    pos.exit_order_id = order_id

# Fixed (D-01):
filled_qty = await self._place_exit_order(pos.code, qty)
if filled_qty > 0:
    pos.remaining_quantity = max(0, pos.remaining_quantity - filled_qty)
    if pos.remaining_quantity == 0:
        # Already set to CLOSED by evaluate_close; ensure it stays CLOSED
        pos.phase = PositionPhase.CLOSED
    pos.updated_at = now_et()
    self._persist_position(pos, event="stop_out_filled")
    # Fire exit alert (D-01)
    if self._on_exit_alert is not None:
        try:
            entry = pos.entry_price or 0.0
            stop = pos.initial_stop or 0.0
            exit_proxy = pos.avg_fill_price or entry

            r_multiple = (exit_proxy - entry) / risk if risk != 0 else 0.0
            self._on_exit_alert(pos.code, pos.pending_exit_reason or "stop_out", round(r_multiple, 2))
        except Exception:
            _logger.warning("on_exit_alert_error", code=pos.code, exc_info=True)
```

**force_close_all already partially correct:** Lines 363-394 in manager.py already call `manage_exit()` and use `filled` to check completeness. The fix is the same as call sites 1/2 above for alert delivery.

### Anti-Patterns to Avoid

- **Do NOT call `BarAggregator.reset_session()` on reconnect.** It clears `_seen_time_keys` which would cause already-processed bars to be re-evaluated. Only call it at genuine session start in `_job_market_open_subscribe`.
- **Do NOT build BarAggregator in `main.py`.** It needs `asyncio.get_running_loop()`, which is only available after `asyncio.run()` starts.
- **Do NOT call `asyncio.get_event_loop()` inside BarAggregator's `on_recv_rsp`.** The loop is passed at construction time. This anti-pattern is documented in bar_aggregator.py lines 76-77.
- **Do NOT gate position management on `_entries_enabled`.** Only the signal → risk → consume_intent entry branch is gated. `position_manager.on_bar(bar)` runs on every closed bar.
- **Do NOT try to match exit fills by exit_order_id after D-01/D-02.** The `_on_exit_fill` path and `_find_position_by_exit_order_id` remain in the code for entry fills but must not be relied upon for exit-alert delivery.

## Common Pitfalls

### Pitfall 1: BarAggregator returns `(ret, data)` from `on_recv_rsp`, not `None`

**What goes wrong:** Caller might expect `on_recv_rsp` to behave like a fire-and-forget callback. Actually it inherits `CurKlineHandlerBase.on_recv_rsp` which returns `(ret, data)`. The SDK requires this return contract.

**How to avoid:** `BarAggregator.on_recv_rsp` already calls `super().on_recv_rsp(rsp_pb)` and returns `ret, data` — this is correct. Do not change the return signature.

### Pitfall 2: `_on_bar_closed` is called from the asyncio loop, not from a coroutine-compatible context

**What goes wrong:** `asyncio.run_coroutine_threadsafe(self._on_bar_closed(bar_data), self._loop)` in BarAggregator schedules the coroutine on the asyncio event loop. If `_on_bar_closed` is a regular function (not `async def`), it cannot `await` its callees.

**How to avoid:** `TradingBot._on_bar_closed` MUST be `async def`. The existing `asyncio.run_coroutine_threadsafe` call already schedules it as a coroutine.

### Pitfall 3: `manage_exit()` blocks the event loop for the duration of exits

**What goes wrong:** `manage_exit()` is an async coroutine that `await asyncio.sleep(...)` polls for fills. On a stop-out with no fills, it can block `_on_bar_closed` for the TTL duration (cfg.exit_ttl_seconds). During this time, subsequent bar pushes are queued by `run_coroutine_threadsafe` but the loop is occupied. This is architecturally acceptable (D-07: exits must complete before the next bar is processed) but means no new entries fire during an active exit.

**How to avoid:** Do not try to parallelize `manage_exit()` with subsequent bar processing. The sequential nature is intentional (D-07: exits-must-complete invariant).

### Pitfall 4: `pos.exit_order_id` references in the codebase after D-02

**What goes wrong:** D-02 retires the `exit_order_id` push-match path for exit-alert delivery. But `exit_order_id` is still a field on `PositionState` and is persisted to the DB. The `_on_exit_fill` and `_find_position_by_exit_order_id` methods still exist in the codebase (for backward compatibility with the entry-fill path which uses `entry_order_id`). The risk is accidentally leaving the `exit_order_id` assignment in the call sites and expecting it to still drive alerts.

**How to avoid:** In both `_trigger_partial_profit` and `_trigger_stop_out`, remove the lines that set `pos.exit_order_id = order_id`. The `exit_order_id` column in the DB can remain (not a schema change) but it will always be None under the new D-01 architecture.

### Pitfall 5: Late-binding `_bar_buffer` before `BarAggregator` starts receiving pushes

**What goes wrong:** If `_job_market_open_subscribe` runs and registers subscriptions BEFORE `TradingBot.run()` has late-bound `_bar_buffer` into PositionManager, the first bars may arrive with `_bar_buffer` still None on PositionManager. However since `BarAggregator` is constructed in `TradingBot.run()` before the scheduler starts, and `_job_market_open_subscribe` fires at 09:30 ET (a cron job), the late-bind at bot startup is always prior to the first K_5M push.

**How to avoid:** Confirm that `BarAggregator` construction and `_bar_buffer` late-bind happen in `TradingBot.run()` before `self._scheduler.start()` is called. The existing `run()` structure already supports this ordering.

### Pitfall 6: reconcile_once() racing with manage_exit() on the same position

**What goes wrong:** If `reconcile_once()` runs (on the asyncio loop) while `manage_exit()` is mid-execution (also on the asyncio loop — awaiting a sleep), Python's asyncio cooperative scheduling means they interleave at `await` boundaries. If `reconcile_once()` marks a position CLOSED (broker said flat) while `manage_exit()` is still executing its retry loop, subsequent `place_order()` calls in `manage_exit()` would attempt to sell a now-CLOSED position.

**How to avoid (D-07):** Implement the "in-flight skip" — in `reconcile_once()`, skip any position where `pos.exit_order_id is not None` (indicating manage_exit was initiated). This is the precise heuristic D-07 specifies. Since D-02 retires the exit_order_id assignment in normal flow, the planner needs a different in-flight marker. Options:
1. Add an `_exiting: set` set on PositionManager that tracks codes currently in manage_exit (added at call, removed after). `reconcile_once()` skips codes in `_exiting`.
2. Check `pos.phase == PositionPhase.CLOSED` — if manage_exit completed since last reconcile, the position is already CLOSED and reconcile_once would correctly skip the externally-closed check.
The planner should choose option 1 (explicit `_exiting` set) since it covers the case where manage_exit is running but has not yet marked CLOSED.

### Pitfall 7: SignalEngine needs `signal_engine` reference wired into RiskEngine for D-09 burst guard

**What goes wrong:** `RiskEngine.__init__` accepts an optional `signal_engine` parameter (line 76-82 of risk_engine.py). If not provided, `note_intent_emitted()` is never called, breaking the D-09 daily cap tally.

**How to avoid:** In `main.py`, construct `signal_engine` first, then pass it to `RiskEngine`:
```python
signal_engine = SignalEngine(cfg=cfg, gateway=gateway, store=store)
risk_engine = RiskEngine(cfg=cfg, gateway=gateway, store=store, signal_engine=signal_engine)
```

## Open Questions (RESOLVED)

> All three questions were resolved during planning (2026-06-24). Annotations point at the implementing plan/task.

1. **`reconcile_once()` store/manager injection path**
   - What we know: Current `reconciliation_loop(interval_s)` signature has no `store`/`manager`/`alerter` params. These are needed for `reconcile_once()` to do the diff and fire alerts.
   - What's unclear: Whether to inject at `reconciliation_loop()` call time or store refs on the gateway at startup.
   - Recommendation: Inject at `reconciliation_loop()` call time (pass `store`, `manager`, `alerter` as parameters). Storing broker-layer refs on a gateway object would cross a layer boundary. The planner should add these params to both `reconciliation_loop` and `reconcile_once`.
   - **RESOLVED:** Plan 06.1-02 Task 2 adds `reconciliation_loop(self, store, manager, alerter, ...)` passing through to `reconcile_once(store=..., manager=..., alerter=...)`. Refs are injected at call time (not stored on the gateway), preserving the layer boundary.

2. **PositionManager `_exiting` set for reconcile race prevention (Pitfall 6)**
   - What we know: `manage_exit()` and `reconcile_once()` both run on the asyncio event loop and can interleave.
   - What's unclear: D-07 says "skip positions with active manage_exit in flight" but does not specify the detection mechanism since D-02 retires `exit_order_id` assignment.
   - Recommendation: Add `self._exiting: set = set()` to `PositionManager`. Add `code` to `_exiting` before `manage_exit()` call; remove after. `reconcile_once()` skips codes in `manager._exiting`.
   - **RESOLVED:** Plan 06.1-03 Task 1 adds `self._exiting: set = set()` to `PositionManager`; both `manage_exit` call sites wrap the call with add/discard. Plan 06.1-02 reads it defensively via `getattr(manager, "_exiting", set())`, so the order in which Plans 02/03 land within Wave 1 is safe.

3. **BarAggregator `reset_session()` call site**
   - What we know: Must NOT be called on reconnect; should be called at genuine session start.
   - What's unclear: The existing code has no call to `reset_session()` anywhere. The natural place is `_job_market_open_subscribe` before subscribing codes.
