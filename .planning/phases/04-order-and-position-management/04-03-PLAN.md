Add the broker order methods the gateway is missing and build the ExecutionEngine that turns a verified OrderIntent into real (paper) orders. The gateway gains place_order (OrderType.NORMAL only, never MARKET), cancel_order (modify_order op=CANCEL), and the refresh_cache=True fill/order/snapshot queries -- all mirroring the existing subscribe/unsubscribe deferred-import + run_in_executor pattern. The ExecutionEngine prices entries at ask+buffer (D-04), runs the TTL poll loop reconciling fills by order_id (EXEC-05), cancel-replaces unfilled entries up to entry_max_retries then abandons (EXEC-03/D-05), accepts partial fills as the position (D-06), and runs exits as escalating marketable limits until flat (EXEC-02/D-07). Every fill becomes a FillEvent the PositionManager consumes.

Purpose: This is the first component that WRITES to the broker. The safety-critical invariants are: SIMULATE-only (EXEC-01), never a market order (EXEC-02), bounded retries so a re-price loop can't spam orders (D-05/D-07), and order_id reconciliation so a partial exit is never misread as a stop-out (EXEC-05). Polling deal_list_query(refresh_cache=True) is the authoritative fill source -- SIMULATE push is officially unreliable. Per D-01 the engine places NO native broker stop order (no OrderType.STOP/STOP_LIMIT/TRAILING_STOP); every stop is the FSM's synthetic close-based stop executed as a marketable-limit exit.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OrderIntent -> broker | the first write to the broker; a wrong env or order type is a real (paper) money action |
| broker fills (deal_list) -> FillEvent | fill rows are broker truth; mis-keying by qty corrupts position/risk state |
| TTL retry loop -> broker | an unbounded re-price loop could spam orders / hit rate limits |
