Design decisions. They were made at planning time and verified on a scratch prototype of these exact changes (1345 passed, 1 skipped). The executor must not re-decide them.

- **CR-03 mechanism: a per-attempt try around everything after `place_order`.**
  - `order_id = await self._gw.place_order(...)` stays the first statement of each attempt. It is the single call site, unchanged.
  - Everything after it in that attempt goes inside `try:`: the on_placed await, the placed log, the poll loop with its full-fill return, the TTL cancel, the re-read with its partial return, and the escalation step.
  - `except GeneratorExit: raise` comes first. A coroutine that is being closed cannot await, so it must propagate untouched.
  - Then `except BaseException:` runs `await asyncio.shield(self._gw.cancel_order(order_id))`:
    - on a successful cancel it logs warning `leg_cancelled_on_error`
    - on a failed cancel it logs error `leg_cancel_on_error_failed` and appends the audit event `leg_cancel_on_error_failed` with `order_id`
    - either way it then runs a bare `raise`
  - Only the order of the current attempt can be live. Every earlier attempt's order was cancelled on the TTL path before the next placement.
- **(a) CancelledError: shield the cancel, then re-raise.**
  - `BaseException` is required because CancelledError has not been an `Exception` since Python 3.8, and `asyncio.run` / APScheduler cancel running job tasks at shutdown.
  - `asyncio.shield` means that a second task cancellation during the await cannot abort the broker cancel.
  - Known limit: at a kill-switch shutdown, `OptionsBot._shutdown` closes the gateway BEFORE `scheduler.shutdown` cancels the job. On that path the cancel fails, and it is logged and audited with the order_id. The row stays OPENING/CLOSING, and the next startup's reconcile alert is the operator's signal, which is why that alert also gets the working-orders hint.
  - Reordering `_shutdown` (cancel and await the jobs before `gateway.close`) is the upgrade path. It is deferred, because it changes shutdown behavior outside this finding.
- **(b) An exception is never converted into a return value.** A partly filled order must never look like "nothing filled" (None) or like a known quantity (a tuple). The exception propagates, and each caller's existing escalation path handles it:
  - the entry unwind: open_position's `except Exception` gives `unwound = False`, then False, then `_try_open` sets NEEDS_ATTENTION (11-08)
  - the manage close: `options_close_error` gives `ok = False`, then NEEDS_ATTENTION (11-07)
  - the opening legs: EX-03, deferred. The row stays OPENING and startup reconcile flags it.
  - Re-polling after the cancel to return an exact partial quantity was rejected. The poll is the call that just failed (typically under the same rate limit), and a guessed quantity would let the unwind treat an unknown as known.
- **(c) The fill_leg docstring's "Guarantee" becomes true, with two limits that the docstring names:**
  - a cancel that itself fails. That case is logged and audited, and the order may still be working.
  - a `place_order` that raises. There is no order_id to cancel in that case.
  - A second cancel of an order that the TTL path already cancelled, or that has just filled, can also fail and log `leg_cancel_on_error_failed`. That is a false alarm on the safe side.
- **CR-03 alerts.**
  - A module constant `_WORKING_ORDERS_HINT = "cancel any working orders on these codes in moomoo before closing manually."` ends three alerts, each of which now names the position's leg codes:
    - `_try_open`'s UNWIND INCOMPLETE
    - `_manage_position`'s "close incomplete"
    - reconcile's startup "restarted mid-opening/closing", which is the only operator signal on the task-cancellation path the review lists
  - **Order ids are NOT added to the alerts, because they are not cheaply available.** The `open_position_unwound` audit carries none: the unwind's `close_legs` runs with no callbacks, and adding them would change the execution contract.
  - After this fix, the only order that can still be working is one whose shielded cancel failed. That order's id is in the new `leg_cancel_on_error_failed` audit event and error log. The codes are what the operator uses in the moomoo app.
- **WR-10 design: a one-time "expiry warning" on the FIRST expiry-day cycle that cannot manage the position. No status change.**
  - Helper: `OptionsBot._warn_expiry_unmanaged(pos, codes, reason, today)`, guarded by `self._expiry_warned` (a set of position_ids).
  - Called from:
    - the WR-06 retry branch when `dte <= 0` (reason `no_quote`), in Task 2
    - the snapshot-outage skip when the position's dte is `<= 0` (reason `snapshot_outage`), in Task 3
  - Why this is the smallest design that holds when every later cycle is dropped: the warning fires on the first expiry-day cycle that reaches the position. Any number of later dropped fires cannot suppress it, and the automated close stays armed.
  - A position that is still OPEN on expiry day with a good quote is closed by assignment_guard on that cycle. With `assignment_guard_dte: 1`, simply being OPEN at dte 0 is already abnormal.
  - Rejected: widening the final window to `now + 2*interval >= cutoff`. It still fails if two fires are dropped, and it hands the position to the operator earlier.
  - Rejected: counting expiry-day misses with threshold 1. That hands the position off at the 09:35 gap and cancels the automated close that WR-06 protects.
  - The existing 3-streak and final-cycle escalations are unchanged.
  - Precondition of the guarantee: at least one manage cycle processes the position on expiry day before the cutoff. A process that (re)starts inside the last interval before the cutoff gets no cycle, which is the same class as the bot being down. It is accepted as T-11-57 and surfaced for an operator decision.
- **WR-06 day-before property:** warnings fire only when `dte <= 0`. The day-before retry path is unchanged: no alert, no status change. It is pinned by the unmodified tests `test_manage_unquotable_near_expiry_final_cycle[day_before_expiry_retries]` and `test_manage_near_expiry_escalates_after_three_consecutive_bad_cycles`.
- **IN-08 design: store `(today, count)` in `self._quote_miss_streak[pid]`.**
  - `today` is the `_manage_position` argument, which `_job_manage` derives from `now_et().date()` (bot/safety/et_helpers.now_et, the project's ET clock). It is never host-local time.
  - Streak rule: `day, prev = self._quote_miss_streak.get(pid, (today, 0)); streak = (prev if day == today else 0) + 1`.
  - Chosen over "clear every streak on the first cycle of a new date": the rule stays in the one place the streak is read, and it also holds when `_manage_position` is called directly. The two existing `pop(pid, None)` calls are unchanged.
- **WR-11 design: a process-level counter `self._snapshot_outage_cycles`, with N = `_QUOTE_MISS_ESCALATE_CYCLES` reused as the review suggests, so no new knob.**
  - It is incremented once per manage cycle with any failed chunk.
  - The alert fires at `==` N, so once per episode.
  - A cycle whose chunks all succeed resets it to 0, which re-arms the alert.
  - A cycle with an empty book takes no snapshot and leaves the counter untouched (no evidence either way). The counter carries overnight because it measures process health, not a session quantity, and that fails toward the human.
  - Per operator scope, outages still never touch the per-position streak. The expiry-day part is the WR-10 warning with reason `snapshot_outage`.
