### Anti-Patterns to Avoid

- **Batching multiple findings into one commit:** Each finding must be an atomic commit with its own failing test first. Batching makes bisect impossible.
- **Writing the fix before the test:** The SPEC explicitly requires failing test first. A passing test written after the fix proves nothing.
- **Mocking too aggressively:** Tests for 1.1 should verify the CALL to `register_position` and `on_fill` via mock assertions, but integration-level tests for _on_entry_fill in `test_manager.py` should use the real manager against a tmp_state_db.
- **Skipping `signal_engine.note_intent_resolved()` on the abandon path:** Both the fill path and the abandon path (fill is None) must call it. The SPEC is explicit: "Both paths call signal_engine.note_intent_resolved()."
- **Treating reconcile failure as "clean slate":** Finding 1.2 root cause — never derive "externally closed" from a failed query. Skip the cycle; do not derive any state transitions.
- **Returning 0.0 from get_bid_price / get_ask_price:** Fix 2.4 requires returning an explicit error sentinel (raise GatewayError or return None). The caller must handle the error; 0.0 silently propagates to negative exit limits.

## Common Pitfalls

### Pitfall 1: Skipping note_intent_resolved on the abandon path

**What goes wrong:** `_pending_count` leaks upward; after `max_concurrent_positions` (5) entries,
`_pending_count >= 5` permanently, blocking all future entries.
**Why it happens:** The fix for 1.1 focuses on the success path (fill is not None) and misses
the `else` branch.
**How to avoid:** The SPEC is explicit: "Both paths call `signal_engine.note_intent_resolved()`."
Write the test to verify the abandon path calls it too.
**Warning signs:** `test_pending_count_decremented_on_abandon` fails; or integration UAT shows
entries blocked after 5 fills.

### Pitfall 2: Treating reconcile_once failure as authoritative (Finding 1.2)

**What goes wrong:** A transient OpenD error causes `position_list_query` to fail → `broker_map = {}`
→ all positions marked externally-closed → stop-loss management abandoned for all open trades.
**Why it happens:** The code pattern `if ret_pos == RET_OK and broker_data: broker_map = {parse...}
else: broker_map = {}` — the else branch silently uses empty.
**How to avoid:** On `ret != RET_OK`: log the error, send an alert, and `return` from the
reconcile cycle immediately. Never populate `broker_map = {}` from a failed query.
**Warning signs:** All positions vanish from in-memory state after a brief OpenD glitch.

### Pitfall 3: APScheduler reschedule_job vs add_job (Finding 1.5)

**What goes wrong:** Calling `add_job` instead of `reschedule_job` creates a second force_close
job. On half-days both fire: one at 12:51 (correct) and one at 15:51 (3 hours after close).
**Why it happens:** Confusing add_job (creates new) with reschedule_job (replaces trigger on
existing job).
**How to avoid:** Use `scheduler.reschedule_job("force_close", trigger=DateTrigger(...))`.
The job must be registered once with a static ID in `_register_jobs()`, then its trigger
updated daily in `_job_premarket_scan`.
**Warning signs:** Multiple force_close jobs visible in `scheduler.get_jobs()`.

### Pitfall 4: Using 0.0 as error sentinel in get_bid_price / get_ask_price (Finding 2.4)

**What goes wrong:** Engine receives 0.0 → computes exit limit as `0.0 * 0.995 = 0.0` → places a
limit order at $0.00 (broker rejects, or worse: fills at market).
**Why it happens:** The current implementation returns `0.0` on failure instead of raising.
**How to avoid:** Return `None` or raise `GatewayError` on snapshot failure. The calling code
in engine.py must retry, then fall back to last bar close price for the exit. A stop-out is
never silently aborted.
**Warning signs:** `GatewayError` on stop-out + silent position leak.

### Pitfall 5: UNIQUE constraint on wrong column (Finding 2.5)

**What goes wrong:** `INSERT OR IGNORE` ignores duplicates keyed by `position_id` (PRIMARY KEY),
not by `code`. Two orphan-adoption cycles for the same symbol insert two rows with different
UUIDs — both get "adopted" and the position ends up double-managed.
**How to avoid:** Add `UNIQUE(code)` to the positions table via a new migration, or add an
application-layer check `WHERE code = ? AND phase != 'CLOSED'` before insert.
**The recommended approach:** Application-layer check (avoids a schema migration risk). Query
for an existing open position by code before inserting the orphan row.

### Pitfall 6: trades table partial-insert (Finding 2.3)

**What goes wrong:** Attempting to write a trade row on entry fails because `exit_price NOT NULL`
and `closed_at NOT NULL`. The insert raises an IntegrityError, the daily_trade_count increments,
but no trade row exists — EOD report still shows 0 trades.
**How to avoid:** Write the complete trade row in `_on_exit_fill` when `remaining_quantity == 0`.
Use the position's `entry_price` and the fill's `avg_fill_price` as exit price.

### Pitfall 7: prior_row staleness after CR-02 (Finding 2.6)

**What goes wrong:** `prior_row = prior_frame.iloc[-1]` takes the last row chronologically before
scan_date. If the data is stale (e.g., yfinance returned last week's data), the prior_close
used for gap% is from an old date → inflated gap → false positives.
**How to avoid:** After taking `prior_frame.iloc[-1]`, verify its date:
```python
prior_date = prior_row.name.date() if hasattr(prior_row.name, 'date') else prior_row.name
if (scan_date - prior_date).days > 5:  # more than one week stale
    return None  # skip symbol
```
The CR-02 fix already handles today-row staleness; this restores the prior-row check that
was inadvertently removed at the same time.

### Pitfall 8: exit_proxy in _trigger_stop_out (Finding 2.7)

**What goes wrong:** `exit_proxy = pos.avg_fill_price or entry` uses the entry price (not the
stop) as the hypothetical exit price for the R-multiple in the alert. R = (entry - entry) / risk
= 0. Alert shows "R: 0.00" which is meaningless.
**How to avoid:** Use the stop price as the exit proxy in the pre-fill alert:
```python
exit_proxy = pos.trail_stop  # the price we're stopping out at
```
The actual fill price will update the R when the exit fill arrives.

## Open Questions (RESOLVED)

1. **How does watchdog get a reference to bot._bar_agg for fix 1.3?**
   - **RESOLVED:** watchdog `__init__` already takes `bot`; `_on_reconnect` calls `gateway.set_handler(bot._bar_agg)` before re-subscribing (per Plan 06.2-01 Task 3).
   - What we know: `watchdog.py:_on_reconnect` calls subscribe but not set_handler. The `bar_agg` lives on the `bot` object. Watchdog has no reference to bot.
   - What's unclear: Whether watchdog already has a handler-registration callback or whether bot needs to pass bar_agg to watchdog at construction time.
   - Recommendation: Pass `set_handler` as a callable to watchdog constructor (or pass bar_agg directly). Check watchdog constructor signature at plan time.

2. **Should fix 2.3 write a partial trade row on entry fill + complete it on exit?**
   - **RESOLVED:** Schema has `exit_price NOT NULL` / `closed_at NOT NULL` — write the complete trade row only at final exit fill (`remaining_quantity == 0`); open-trade view derives from the positions table (per Plan 06.2-02 Task 3).
   - What we know: The trades table schema has `exit_price NOT NULL` and `closed_at NOT NULL`. A partial row cannot be inserted on entry.
   - What's unclear: Whether the SPEC intends the entry-fill hook to write an "open trade" row to a separate table, or simply accumulate state in memory until the exit fill.
   - Recommendation: Based on schema constraints, write the complete row at final exit fill. If an "open trade" view is needed for reporting, it can be derived from the positions table (which already has all fields).

3. **Fix 3.2 scope: where does the day-cache live?**
   - **RESOLVED:** Caller-owned in-memory dict on the TradingBot object (`self._daily_bar_cache`, keyed on trading date), not a module-level singleton or file cache (per Plan 06.2-03 Task 2).
   - What we know: `_job_intraday_rescan` re-downloads the full 500-symbol universe each call.
   - What's unclear: Whether the cache should be an in-memory dict on the bot object (keyed on `date.today()`) or a file-based cache.
   - Recommendation: In-memory dict on the bot object (simplest; survives intraday restarts within the same process but not across restarts — acceptable for this use case).
