<objective>
Close the single major UAT gap on ALERT-02: the PositionManager → TelegramAlerter exit-alert integration does not satisfy "On each exit, a Telegram alert fires covering all five exit reasons — partial, breakeven move, trail-stop, stop-out, force-close." Three concrete defects: (1) `_on_exit_fill` calls `on_exit_alert` with a hardcoded `"exit_fill"` reason so every live exit renders "Exit Fill"; (2) the exit alert is gated on `remaining_quantity == 0`, so partial scale-outs (which leave shares open) fire NO alert; (3) the alerter's `_EXIT_REASON_LABELS` is missing the `trail_stop` key the manager emits, so a trailing-stop exit would render its raw string even once the real reason is passed.

Fix approach (FSM-consistent, order_id-keyed, no DB schema change, no strategy-logic change): record the true exit cause on the in-memory `PositionState` at the FSM trigger point (`_trigger_stop_out` / `_trigger_partial_profit` / `force_close_all`), then read it back in `_on_exit_fill` when the broker fill arrives and pass it to `on_exit_alert`; fire the partial alert immediately at the scale-out trigger; and add `trail_stop` to the label map so the reason vocabulary reconciles.

Purpose: The operator must be able to tell WHY a position closed from the Telegram alert — a stop-out, a trail-stop, a breakeven stop, a partial profit-take, or the EOD force-close — exactly as ALERT-02 requires. Today every live exit looks identical ("Exit Fill") and partials are silent.
Output: `pending_exit_reason` field on PositionState; real-reason plumbing + partial alert in PositionManager; `trail_stop` added to the alerter label map; new tests asserting each of the five reasons alerts correctly and that a partial scale-out fires an alert. Green tests/position + tests/service; full suite stays at 393+ passing.
</objective>
